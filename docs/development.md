# Development process

The lifecycle controls this repository follows. They are light, but each step
leaves a record.

## Branches and pull requests

- `main` is always releasable: tests pass and model cards match the code.
- Work happens on a branch named for the change, e.g. `feature/stress-by-month` or
  `fix/roll-day-scenarios`.
- Each branch is merged through a pull request, using the checklist in
  `.github/pull_request_template.md`. CI must pass before merging.

## Tests

- `pytest` runs the suite; `pytest --cov=erl` shows coverage.
- A new risk measure comes with at least one test against a known answer (closed form,
  hand-calculated example or textbook statistic), not only "it runs".
- A bug fix comes with a test that failed before the fix.

## Style

- `ruff check .` (lint) and `ruff format .` (formatting) before each commit.

## Model changes

A change that alters a number (method, parameter, data treatment) updates the model
card in `docs/model_cards/`: method, assumptions, limitations, the tests, and a line in
its change log.

## Versions and releases

- Semantic versioning: 0.x while in development; the minor version goes up with each
  roadmap item.
- Each release is listed in `CHANGELOG.md` and tagged: `git tag -a v0.1.0 -m "v0.1.0"`.

## Dependencies

- `pyproject.toml` gives the supported ranges.
- For an exact record of a working environment:
  `pip freeze --exclude-editable > requirements-lock.txt`, committed with the release.
  `pip install -r requirements-lock.txt` rebuilds it.

## Data

- Data and outputs are generated by code and never committed (see `.gitignore`).
- No real positions, prices or company names: synthetic data only.
